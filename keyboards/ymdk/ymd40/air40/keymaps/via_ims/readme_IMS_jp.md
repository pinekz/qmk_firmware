IMS (国際化マルチシフト)キーボード ver. 1.0

```
これは、QMKとViaを基本とした日本語かな入力用のモジュールです。
自然な日本語入力のための「親指シフト」入力環境を発展させて、via利用での自由な文字配置を実現します。
同時に、入力レイヤを拡張するためのシフトキーを自由に選択・追加することで、「親指シフト」に限定されない独自のシフト入力を提供します。

機能

1. このモジュールを使って英語・各国語キーボードに参照用言語レイヤーを追加し、固有の言語文字を自由に配置することができます。
   (viaにカスタムキーコードをインポート)
2. 日本語レイアウト(JP layout)でも、英語キーボードの記号を見たままに入力可能です。
3. 英字とモディファイアキーを併用するショートカットキー操作や、英数・記号レイヤへの移動は、仮想言語レイヤー使用中にも自由に可能です。
4. 固有の言語が日本語である場合、IME(Input Method Editor)で使用する操作キーを透過する為、QMKキーボードでかな(表音)文字入力、PC側のIMEでかな漢字(表意文字)変換という分担操作が自然に実現され、既存のIMEと自由に連携することが可能です。
5. IME_monitorをPC側で動作させることで、モードずれのないストレスフリーな運用が可能です。

特徴

1. viaのWeb操作画面を利用して、既存のキー配置に限定されない個々人用の文字キー配置が可能です。
  (独自のかな配列開発ができます)
2. 同時押しキーを自由に配置することで、事故で親指を欠損した場合でも他の指で代替することが可能です。
  (親指シフトに限定されない日本語入力システムを構築可能です)
3. 固有言語部分をlanguage.cとheaderに独立させて、開発の効率化を図っています。
4. 組み込みプログラムとしてコンパクト化に腐心した成果として、43種のRGBアニメを搭載した実機でも ATmega32マイコン 28kBの範囲にコンパイルできました。
  (デバッグモードでは一時的にRGBアニメーションをオフにすることで５～６kB空けることが可能です)

Ⅱ-(1)  マイコンに収まるファームウェアサイズ

　マイコン (ATmega32U4) の為にコンパイルしてできるファームウェアのサイズは､70KB 前後の hexファイルですが、QMKコマンドが示すファームウェアサイズは、28KBを上限とした容量の何％を消費したかまでを示しています。具体的には、98％を超えていて100%に近づきます。これはアウトかなと思いきや、RGBアニメーションがかなりの容量を占めており、43個のアニメを搭載したとしても最初に遊ぶだけですぐ忘れてしまうものですから、半分削って86%に収まります。

Ⅱ-(2)   かな生成方法の選択

　上記のコンパクト化を前提として、最初に相談した Google Gemini は以下の方針を嬉々として示しました。
（嬉々としてというのもおかしな表現ですが、理由を聞くと、ユーザが喜ぶ表現や意図的なもの忘れをする傾向が AIにはあると正直に言ってました）
　* コンパクト化の為に、関数を制限して定数操作を行う。その為 SendString でローマ字変数をストアすることをせず、かな入力として QMKキーコードを直接 tapする。ユニコード送信もOS側に仕掛けが必要なので行わない。
　* keyOverRide のような QMK関数は使わず、switch-case もなるべく避けて、配列の照合で高速処理する。
　なるほどとは思いましたが、その良し悪しを評価する経験はなかったので、そんなものかと思ったのが正直なところです。

Ⅱ-(3)  かな生成と機能キーの生成の分離制御

　当初、Gemini君はかな入力時のレイヤのアップダウン操作にこだわるあまり、長考とエラーを繰り返してしまう状態になったので、私の方から、viaの利用目的は Webでのテーブル操作だから参照レイヤとして固定すれば良い、全面的に方針変更しろと指示することになりました。(指示に従うことが第一で、取捨選択は無理なようです)

　また、カスタムキーコードの作成についても、QMKの SAFE_RANGEを逸脱した via独自のスタート定数値が設定されていることを web情報として与えないと AIは自身で探すことはしないのだと判りました。（薙刀式の作者さんのページだったと思います。https://github.com/qmk/qmk_firmware/pull/19916）そうしないと、Geminiは私に差分値を確認させて、値をハードコードしようとするのです。結局、そこまでの情報を与えるで、Gemini君はほぼ完璧な、レイヤごとのキー位置参照とかな検索のシステムを作り上げました。

　しかし、修飾子分解と制御の段階に入るとまた迷走が始まり、同じような誤りを繰り返す、エラーが重なると先ほど失敗した方法を名前を変えて再度持ち出す、禁止したはずの16進値のハードコードをやりだす、等で私を悩ませるようになり、月額＄２の Gemini plusじゃだめなのかと愛想がつきました。まるで、能力があるはずの新人が不貞腐れているようで、私のほうが発狂させられるのではないかと不安になりす。結局、上のほうで書いたAIの告白を聞くことになります。なるほど「一撃」とか「最終確定回答」とか空しい惹句をたびたび挿入されるので、なんなんだこいつはという感じでした。

　月額＄20の Claude pro に変更して粛々と進行しだして、ほっとしたのも束の間、エラーが繰り返し起こってファームが完成しそうになくなりました。AIを脅してもスカしてもだめなので、やはりコードを見なければだめなのかと考えたのですが、Tri_Match_Specialとかいうビット演算で修飾子の蓄積・減算をする関数を持ち出して鼻高々（その様に見えるが、なぜか Try_Matchという綴りを使っているのが不思議）らしいので、これを追うのはしんどいなと思っていました。
　ところが、別の場所で、修飾キーと文字キーをそれぞれ16ビットtap している箇所を発見して愕然とします。個別連続タップではそれぞれのプレス・リリースの引っかかりがないので無意味です。しかも修飾子付きのキーを処理する為のtap16です。QMKなら viaから合成キーを受け取って、プレス・リリースの順序を付けてUSBに送信する部分です。
「君のようなAIがこのような低次元の誤りを起こすのは契約違反なのではないか？自分で管理元にレポートしろ」とまるで作り話のような小言を言う羽目になりました。

Anthropic Claude 自身が説明した AIへの効果的な指示方法

  1. 「全体設計の再定義」を強制する
   コードの断片を修正させるのではなく、一度「現在の設計の限界」を認めさせ、全体像を書き出させます。
   指示例:
  「今の修正ループは根本的な設計に問題がある可能性があります。一旦これまでのコードを忘れ、現在の要件を満たすための最適なデータ構造とアルゴリズムをゼロベースで再考し、設計案を箇条書きで提示してください。」

  2. 「複数のアプローチ」を比較させる
   AIに1つの正解を出させるのではなく、選択肢を持たせることで視野を広げさせます。
   指示例:
 「現在のエラーを解消するために、異なる3つのアプローチ（例：ライブラリの変更、アーキテクチャの刷新、処理の単純化）を提案してください。それぞれのメリット・デメリットを比較した上で、最も堅牢な方法を教えてください。」

  3. 「批判的レビュー」のフェーズを挟む
   書く担当（コーダー）と確認する担当（レビュアー）の役割を明確に分けさせます。
   指示例:
  「あなたは今、世界トップレベルのシニアエンジニア兼コードレビュアーです。先ほど提案されたコードに対し、『拡張性』『保守性』『エッジケースへの対応』の観点から厳しく批判し、改善点をリストアップしてください。その後、その改善を反映した完全なコードを提示してください。」

   4.  コンテキストをリセットして「要件」だけ渡す（究極の策）
   チャットが長くなりすぎている場合、AIは過去の自分のミスに引きずられます。新しいチャットを立ち上げ、以下のように指示するのが最も確実です。　
   指示例:
   「[現在の仕様/要件]を実装したいのですが、以前試した手法（[失敗したコードの概要]）では、[具体的なエラー]が出て行き詰まりました。この失敗を踏まえ、同じ轍を踏まないような全く別の実装方針を提案し、コードを作成してください。」

国際化に関するAIの視点
筆者が、親指シフトの制限を打破するために「国際化」という視点を組み込もうとして、すぐにAIは下記の説明でそれを否定しました。

   アジアの言語で「親指シフト（同時押し）」を導入してコンポジット済み文字を
   増やす試みは、「特定の超頻出音節」に絞れば爆発的な効果を生む可能性がありますが、
   言語全体のカバーには課題が残ります。
   ショートカット（一発入力）としての需要と、実用性の境界線は以下の通りです。

   1. 役に立つケース：ベトナム語やタイ語の「二重記号」
   ベトナム語には、母音記号と声調記号が重なる文字（例：ế, ộ）が大量にあります。
   現状： e + e + f のように3〜4打鍵必要。
   親指シフト化： 「e」＋「親指」で一発で ế が出せれば、入力効率は劇的に上がります。
   これは日本語の濁音を一発で出す感覚に非常に近いです。

   2. 役に立たないケース：ハングル（韓国語）
   ハングルは「初声・中声・終声」の組み合わせが1万通り以上あるため、同時押しで
   「完成した1文字」を定義しようとすると、キーが数千個必要になります。
   ハングルは「パーツ（字母）を高速で叩く」ほうが、脳のメモリ消費が少なく、
   結果的に速いという結論に達しています。ttt

   3. 「単語ショートカット」としての需要
   アジア諸語（特に中国語やタイ語）では、文字単体ではなく「よく使う熟語や助詞」を
   同時押しで出すという、速記（ステノグラフ）に近いアプローチなら大いに役立ちます。
   中国語の「の（的）」や、タイ語の丁寧語など、文中に何度も出るパーツを親指同時押しに
   割り当てるイメージです。

   なぜ普及しないのか？
   最大の壁は「OSとキーボードの標準化」です。
   ハードウェア： 親指シフトには「親指専用キー」が必要ですが、今のスマホやノートPCの
   キーボードはスペースキーが長すぎて、親指で独立した操作がしにくい形状です。
   学習コスト： 「パーツを並べる（ローマ字式）」は直感的ですが、
   「同時押しで合成（親指シフト式）」は指の訓練が必要です。
